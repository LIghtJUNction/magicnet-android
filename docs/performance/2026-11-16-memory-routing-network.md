# MagicNet 内存、路由与网络实机调优

日期：2026-11-16。实施代码：[`be00fa78`](https://github.com/LIghtJUNction/magicnet-android/commit/be00fa78f2e26a4d6998eb64e181de4028056aff)；对照源码：`b6f3a37fb5d035105917f844a6a23bb499bc1a61`。逐次测量、失败样本、编译身份和最终设备回读见 [evidence.json](2026-11-16/evidence.json)。

## 交付结果

本轮保留了两项源码修复，并将重新构建的 ARM64 CLI 安装到已连接的开发手机。对这台手机额外保留了 `experimental.debug.gc_percent=50` 的配置覆盖：四段同类负载对照中，核心 PSS 加按比例分摊的交换内存，在两次候选阶段分别比对应默认阶段减少约 **17.2% 和 22.9%**。这是单台设备、短时间窗口的结果；项目的全局默认值未改变。

最终回读：核心生命周期 `ready`、数据面就绪、API 就绪、联网检查取得 HTTP 204，配置版本与活动版本均为 3，无待应用修改。测试 APK 已卸载，本轮设备暂存文件已清理。模块显示的发行身份仍为 v1.8.7 / 10615；本轮替换的是手机模块中的 CLI 组件，没有创建新的正式发行包。

公网测试没有形成整体提速结论。国内下载保持约 31 Mbit/s 的两轮中位数，海外下载在两轮都出现超时。下面分别说明设备 GC 参数、CLI 临时分配、路由结构和公网观察，避免混用指标。

## 1. 手机核心内存：默认 / 50 / 默认 / 50

### 实验设计

设备为 PHK110、Android 16、arm64-v8a。运行核心为 `1.15.0-alpha.13+LIghtJUNction.d850ff0ff68e`，Go 1.26.7；核心提交固定为 `d850ff0ff68e11a71aa8207627e0a826cb52808f`。GOMEMLIMIT 保持 512 MiB，TUN MTU 保持 1400，DNS 缓存容量保持 4096。

每个阶段均经现有生命周期入口重启，等待数据面与 API 就绪，再等待 10 秒。普通非 root Android 应用先下载 1 MiB 作预热，然后执行两次 8 MiB TUNA HTTPS 前缀下载。负载前后各读取五次 `/proc/<core>/smaps_rollup`，间隔约 0.4 秒；每阶段检查进程启动标识不变。

比较的是负载后五个采样点的 `Pss + SwapPss` 中位数。PSS 把共享页按使用者分摊，SwapPss 对交换页采用同样口径，因此不把“内存转移到交换空间”误写成释放。本轮四段负载后的 SwapPss 都为 0。五个相邻采样点用于描述该窗口，不视为五次独立实验。

| 阶段 | gc_percent | PSS + SwapPss 中位数 | MiB | 两次 8 MiB 下载（Mbit/s） | 成功 |
| --- | --- | ---: | ---: | --- | ---: |
| A1 | 缺省 | 104,068 KiB | 101.63 | 30.188 / 33.979 | 2/2 |
| B1 | 50 | 86,193 KiB | 84.17 | 33.091 / 37.596 | 2/2 |
| A2，恢复原设置 | 缺省 | 108,537 KiB | 105.99 | 31.345 / 41.891 | 2/2 |
| B2，再次应用 | 50 | 83,647 KiB | 81.69 | 34.135 / 37.638 | 2/2 |

A1→B1 减少 17,875 KiB，约 17.2%；A2→B2 减少 24,890 KiB，约 22.9%。第二次候选阶段还通过 Google 204 与百度 200 检查，耗时分别为 2,472 ms、309 ms。最终额外快照为 RSS 83,984 KiB、PSS 82,907 KiB、SwapPss 0；该快照不替代上表的受控窗口。

保留候选前采用的工程门槛是：相对两个默认阶段中较低的内存值至少下降 10%，两次下载均成功，下载中位数不低于较低默认阶段的 90%，且最终连通性与配置一致性通过。该门槛只决定本设备是否保留候选，不是通用产品性能预算。

### 为什么采用这个参数

垃圾回收的作用是识别并回收已经失去用途的对象；更积极地触发回收，可以减少等待下一次回收期间占用的堆空间，也可能增加回收工作。本轮在固定核心中核对了 [debug.go](https://github.com/LIghtJUNction/sing-box/blob/d850ff0ff68e11a71aa8207627e0a826cb52808f/debug.go)：非空 `gc_percent` 进入 `debug.SetGCPercent`。单独设置这个字段不会开启调试监听服务。

该核心每次成功启动都会执行返还空闲内存的 [FreeOSMemory 启动步骤](https://github.com/LIghtJUNction/sing-box/blob/d850ff0ff68e11a71aa8207627e0a826cb52808f/cmd/sing-box/cmd_run.go)。因此所有比较阶段都重启并采用相同预热流程，不能把启动后的下降全部算成参数收益。

本轮通过已有 override 的预览、版本检查、保存和应用事务操作，A2 实际验证了恢复原覆盖配置。最终仅保留本设备的 `gc_percent=50`；活动配置除这一字段外与原配置完全一致，路由与 DNS 数组逐项相同。没有降低 GOMEMLIMIT，也没有改动全局默认 GC 策略。

CPU ticks 在四个窗口分别增加 99、55、58、47，但窗口随下载耗时变化，不能由此推导 CPU 或续航改善。尚未测量全天负载、长连接、UDP/QUIC、耗电与温度；短测中的下载正常不构成这些指标的保证。

### 保留的失败记录

第一次启动对照时，`cli service restart` 返回非零，尚未应用候选覆盖；该次 stderr 未保存，原因未确定。后续单独诊断重启成功，墙时 42.587 秒；之后 A1/B1/A2/B2 完成。初次失败单独保存在证据中，没有用后续成功覆盖它。

## 2. CLI 本地 HTTP：在接收时落实调用方预算

此前原生 loopback HTTP 回退路径先按传输层 8 MiB 上限接收，再由 WebUI 调用者检查自己的 1 MiB 正文预算。超限数据最终被拒绝，但临时内存和读取工作已经发生。

现在调用方预算进入接收层：能从 Content-Length 判断超限时立即拒绝；没有长度头时，最多读取预算加一个溢出判定字节，再返回错误。总上限、独立首行预算、超时、回环地址约束及 HTTP framing 检查继续保留。

### 受控回环基准

同一开发机、同一编译器和优化参数，服务端提供 8 MiB 正文，调用方预算 1 MiB。每个版本、每种 framing 预热一次后测量七次，共 28 次，均得到预期超限拒绝。峰值来自只覆盖客户端请求线程的 allocator 计数，表示尚存活分配的请求字节数。

| 场景 | 修改前请求峰值堆 | 修改后请求峰值堆 | 降幅 | 初次拒绝耗时中位数 |
| --- | ---: | ---: | ---: | --- |
| 有 Content-Length | 8,388,842 B | 8,467 B，约 8.27 KiB | 99.90% | 4,549 → 1,201 µs |
| 无长度，关闭连接定界 | 8,388,842 B | 1,048,851 B，约 1 MiB | 87.50% | 4,036 → 1,983 µs |

有长度场景的候选实际读取范围为 63–8,192 B，因为头与部分正文可能在一次读取中同时到达；无长度场景实际读取 1,048,615 B，包含 38 B 头部和一个溢出判定字节。服务端 socket 接受的写入量与客户端实际读取量分开记录。

已把 [复现工具](../../scripts/benchmarks/http-response-limit/README.md) 保存到源码仓库，并用新入口独立再运行 28 次。两种场景的峰值堆数字完全复现；重跑耗时中位数分别为 5,720→221 µs、4,815→1,768 µs。有长度场景重跑实际读取中位数为 8,192 B，仍处于原范围内，说明调度和分包会影响短时计数与耗时。

这项结果不表示核心 RSS、Go 堆或手机整体内存同比下降，也不表示有效下载吞吐提升。设备上存在可信 curl，这项改动主要保护原生 HTTP 回退路径；前一节的核心内存收益来自独立 GC 参数实验。

## 3. 路由：消除可证明冗余，保留匹配语义

优化器现在识别紧邻前一条终止型 53 端口 DNS 劫持规则的完整覆盖，避免再次插入已被覆盖的入站快速规则；也能移除精确匹配的旧生成冗余项。只合并相邻、相同出口、无其他匹配条件的纯 rule_set 分发，同时正确处理标量和列表，并稳定去重。部分覆盖、条件差异和有状态动作之间不合并。

| 对同一实机配置的处理 | route 规则数 | DNS 规则数 |
| --- | ---: | ---: |
| 实机原配置 | 63 | 27 |
| 旧优化器输出 | 64 | 27 |
| 新优化器输出 | 63 | 27 |

新优化器输出与设备已有规则相同，并通过幂等检查。这台手机本来就没有那条冗余规则，所以本轮没有把设备从 64 条改到 63 条；修复防止后续构建重新添加它。54 个规则集均被引用，没有以减内存为由删除业务规则集。

控制器观察到 TUNA 走 TUN 入站和直连链，Cloudflare 下载走 TUN 入站和代理链。探针自身验证了非 root 应用身份；此版本控制器连接元数据没有 UID 字段，因此逐连接归属保留为 unknown，不能声称覆盖所有应用或精确证明每一条连接的 UID。

## 4. 公网速度：完整记录成功与超时

在修改 GC 参数之前，分别于 CLI 替换前后执行两轮普通应用 HTTPS 探针。每轮含三个目标各三次小请求，以及国内、海外各三次 8 MiB 下载。该阶段未重启核心，路由配置未改变，未手动切换节点；两轮属于连续观察，不是隔离网络条件下的代码因果实验。

| 目标 | 前轮 | 后轮 |
| --- | --- | --- |
| Google 204 请求中位数 | 3,709 ms，3/3 成功 | 2,052 ms，3/3 成功 |
| 百度请求中位数 | 443 ms，3/3 成功 | 392 ms，3/3 成功 |
| Cloudflare trace 中位数 | 1,124 ms，3/3 成功 | 590 ms，3/3 成功 |
| 国内 8 MiB 下载中位数 | 30.812 Mbit/s，3/3 成功 | 30.798 Mbit/s，3/3 成功 |
| 海外 8 MiB 下载 | 30.826、37.617 Mbit/s；另一次超时 | 37.787 Mbit/s；另两次 ADB 探针超时 |
| 全轮成功数 | 14/15 | 13/15 |

后轮两次 ADB 超时缺少有效完成耗时；记录中的 0 是缺失占位，不作为“0 ms 成功”参与统计。8 MiB 前缀吞吐包含建连等开销，不等同于长时间链路带宽。

核心在这两轮负载后的 PSS 中位数分别为 79,468 与 85,732 KiB，Swap 为 15,092 与 15,060 KiB，不能写成 CLI 替换降低了常驻内存。它们与重启后、固定年龄的 GC 四段实验属于不同观察条件。

目前能够确定国内下载可用、分流方向符合配置；海外性能仍有波动。没有足够证据把瓶颈归因于某个节点、DNS、MTU 或规则查询，因此本轮保留 DNS、MTU、节点选择和规则集，不宣称公网提速。
